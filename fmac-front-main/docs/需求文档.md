# 2. 项目背景

## 2.1 当前项目是什么

fmac-front-main 是一个企业级前端系统，采用 **layout 基座 + 多个子应用** 的架构，服务于企业内部多个业务模块（仓储管理 wms、资金结算 frs、OCR 识别 ocr、图片管理 pic、平台管理 platmng、资金调度 fndrsch、工作流 workflow）。所有应用部署在同一域名下，由 layout 基座统一管理菜单、登录和子应用加载。

## 2.2 当前技术/架构现状

当前系统采用传统架构：

- 一个 layout 基座负责统一入口、菜单管理、登录认证和子应用加载
- 多个子应用（wms、frs、ocr、pic、platmng、fndrsch、workflow）共享同一基座
- 所有应用部署在同一域名下
- 各子应用的构建、部署方式不统一

## 2.3 为什么需要进行本次项目

随着业务增长，现有架构暴露出多个严重问题，已无法满足业务发展和工程维护的需要。需要引入基于 **qiankun 微前端** 的新框架基座（main-layout），对老系统进行全面改造。

## 2.4 当前存在的主要问题

1. **子应用之间缺乏隔离**：样式冲突频发，全局变量相互污染，一个子应用的异常可能影响其他子应用
2. **layout 基座耦合严重**：新增或修改子应用需要改动基座代码，维护成本高
3. **缺少企业级 Layout 能力**：没有标签页管理、页面缓存等企业后台系统必备能力
4. **构建部署不统一**：各子应用构建和部署方式不一致，增加运维复杂度
5. **开发效率低下**：子应用无法独立开发和调试，每次修改需要启动整个系统

## 2.5 原有方案存在什么限制

- 子应用无法独立部署，必须跟随基座一起发布
- 子应用技术选型受限，无法根据业务特点选择合适方案
- 基座代码膨胀，难以维护和迭代
- 缺乏标准化的子应用接入规范

## 2.6 为什么现阶段需要解决这些问题

- 业务模块持续增长，子应用数量将不断增加，现有架构的扩展瓶颈已经显现
- 样式冲突和全局变量污染导致线上问题频发，影响用户体验
- 缺乏标签页管理等核心能力，用户操作效率低下
- 需要建立标准化的子应用接入规范，为后续业务扩展奠定基础

# 3. 项目现状

## 3.1 当前架构

项目采用 **qiankun 微前端** 架构，由新框架基座 main-layout 替换老 layout：

```
现有架构：

fmac-front-main/
├── main-layout/          # 主应用（微前端基座）
│   ├── src/
│   │   ├── api/          # API 接口层
│   │   ├── layout/       # 布局组件（Layout、AppHeader、AppSidebar、AppTabBar）
│   │   ├── micro/        # 微前端核心（子应用注册、全局状态）
│   │   ├── platform/     # 平台能力（session 超时检测、通信桥梁）
│   │   ├── router/       # 路由（守卫、路由定义）
│   │   ├── store/        # Vuex 状态管理（token/userInfo/menu + tabs）
│   │   ├── utils/        # 工具函数（auth、logout、request、message）
│   │   ├── views/        # 页面（Login、Home）
│   │   ├── App.vue
│   │   └── main.js       # 入口（qiankun 生命周期）
│   ├── mock/             # Mock 数据
│   └── webpack.config.js
│
├── app-demo/             # 子应用示例
│   ├── src/
│   │   ├── api/
│   │   ├── router/
│   │   ├── utils/
│   │   ├── views/
│   │   ├── context.js    # 通信模块
│   │   ├── public-path.js # 动态资源路径
│   │   └── main.js       # 入口（qiankun 生命周期）
│   ├── mock/
│   └── webpack.config.js
│
├── deploy/nginx/         # Nginx 配置
└── docs/                 # 项目文档
```

# 4. 项目目标

## 4.1 技术目标

1. 建立基于 qiankun 2.x 的微前端基座，实现子应用的动态注册、加载和卸载
2. 实现主子应用双向通信机制，支持状态同步和事件通知
3. 统一 token 认证规范（localStorage key: fmac_token），主子应用共享认证状态
4. 实现统一的 401/418 异常处理，子应用异常时通知基座统一退出

## 4.2 架构目标

1. 用 main-layout 替换老 layout 基座，提供统一的登录、菜单、标签页、通信等能力
2. 实现子应用之间的完全隔离（样式隔离、JS 沙箱），消除样式冲突和全局变量污染
3. 建立标准化的子应用适配规范，每个子应用仅需新增 3 个文件 + 改造 2 个文件即可接入
4. 支持子应用独立运行和 qiankun 加载两种模式

## 4.3 工程化目标

1. 各子应用保留原有工程结构和独立仓库，不采用 monorepo
2. 各子应用独立构建、独立部署，通过 URL 被基座加载
3. 统一构建工具为 Webpack 4，统一配置体系为 CommonJS
4. 统一环境变量管理（.env.dev / .env.test / .env.prod）

## 4.4 开发体验目标

1. 主应用和子应用可独立启动和调试
2. 子应用适配改造量小（约 5 个文件），不影响业务代码
3. 提供 app-demo 示例工程，作为子应用接入参考
4. 标签页管理支持拖拽排序、双击关闭、右键菜单等企业级交互

## 4.5 维护性目标

1. 基座代码模块化（layout、micro、platform、router、store、utils），职责清晰
2. 子应用适配使用统一模板，降低维护成本
3. 后续可将适配代码抽取为公共 npm 包（如 `@fmac/subapp-sdk`）

## 4.6 兼容性目标

1. 兼容 Node.js 18 运行环境
2. 兼容 Webpack 4 构建体系
3. 兼容 Vue 2.7.x 框架版本
4. 兼容各子应用现有技术栈（假设均为 Vue 2.x + Webpack）
5. 适配后子应用仍可在非 qiankun 环境下独立启动

## 4.7 稳定性目标

1. 新老系统可并行运行，支持灰度切换，降低业务中断风险
2. 渐进式接入子应用，分三批改造，优先验证最复杂的应用
3. 基座具备 Session 超时检测和自动退出能力
4. 标签页状态支持持久化，浏览器刷新后可恢复

## 4.8 可扩展性目标

1. 新子应用可通过标准化流程快速接入
2. 后端菜单接口驱动子应用注册，无需硬编码
3. 通信协议可扩展，支持新增事件类型

# 6. 功能需求

> 本项目属于框架迁移和工程改造项目，以下按功能模块组织，而非传统业务系统的功能划分。

## 6.1 微前端核心能力

### 6.1.1 子应用动态注册

- **功能目的**：根据后端菜单数据动态注册子应用到 qiankun，无需硬编码
- **功能描述**：基座从后端菜单接口获取子应用列表，提取包含 entry 的菜单项，动态生成 qiankun 子应用配置
- **输入/触发条件**：登录成功后获取菜单数据
- **处理逻辑**：过滤菜单数据中有 entry 字段的项，映射为 `{ name, entry, container, activeRule }` 格式
- **输出/结果**：qiankun 注册对应子应用，访问对应路由时自动加载
- **异常情况**：菜单数据为空时返回空数组，不注册任何子应用
- **相关约束**：子应用 entry 和 route 由后端菜单接口配置

### 6.1.2 子应用加载与卸载

- **功能目的**：实现子应用的生命周期管理
- **功能描述**：qiankun 在路由匹配时自动加载子应用，路由离开时自动卸载
- **输入/触发条件**：用户访问子应用路由
- **处理逻辑**：qiankun 调用子应用的 bootstrap → mount 生命周期；路由离开时调用 unmount
- **输出/结果**：子应用正确渲染在 `#subapp-container` 容器中
- **异常情况**：子应用加载失败时显示错误提示
- **相关约束**：子应用必须导出 bootstrap、mount、unmount 三个生命周期函数

### 6.1.3 样式隔离

- **功能目的**：防止子应用之间以及子应用与基座之间的样式冲突
- **功能描述**：开启 qiankun experimentalStyleIsolation，自动为子应用样式添加作用域前缀
- **输入/触发条件**：qiankun 加载子应用时自动生效
- **处理逻辑**：qiankun 在子应用容器上添加特定属性选择器，子应用 CSS 编译时自动添加前缀
- **输出/结果**：子应用样式仅在自身容器内生效
- **异常情况**：部分第三方库的内联样式可能无法隔离，需子应用自行处理
- **相关约束**：子应用 DOM 操作需限制在自身容器内

## 6.2 认证与安全能力

### 6.2.1 Token 管理

- **功能目的**：统一管理用户认证令牌
- **功能描述**：使用 localStorage 存取 token（key: fmac_token），基座和子应用共享同一 token
- **输入/触发条件**：登录成功时存储，退出时清除
- **处理逻辑**：`utils/auth.js` 封装 token 的存取方法
- **输出/结果**：各模块通过统一接口获取 token
- **异常情况**：token 缺失或过期时跳转登录页
- **相关约束**：所有应用使用统一的 localStorage key（fmac_token）

### 6.2.2 Session 超时管理

- **功能目的**：检测用户操作状态，超时自动退出
- **功能描述**：监听 mousemove/keydown/click 事件，30分钟无操作自动退出登录
- **输入/触发条件**：用户登录成功后启动 session 监听
- **处理逻辑**：`platform/session.js` 记录最后活跃时间，定时检测是否超过 30 分钟
- **输出/结果**：超时后自动清除 token、通知子应用退出、跳转登录页
- **异常情况**：浏览器关闭后 session 监听自动停止
- **相关约束**：超时时间固定为 30 分钟

### 6.2.3 统一退出流程

- **功能目的**：确保基座和所有子应用同步退出
- **功能描述**：退出时基座通过 bridge 通知所有子应用清除状态，子应用通过 `window.microApp.logout` 通知基座
- **输入/触发条件**：用户主动退出、session 超时、401/418 异常
- **处理逻辑**：`utils/logout.js` 统一协调退出流程
- **输出/结果**：所有应用清除 token，跳转登录页
- **异常情况**：子应用未挂载时通知可能无法送达，但不影响基座退出
- **相关约束**：子应用需在 mount 时暴露 `window.microApp.logout`

## 6.3 路由与导航能力

### 6.3.1 路由守卫

- **功能目的**：控制页面访问权限，自动维护页面标题
- **功能描述**：beforeEach 守卫校验登录状态，未登录跳转登录页；afterEach 设置页面标题、自动创建标签
- **输入/触发条件**：每次路由跳转
- **处理逻辑**：
  - beforeEach：检查 token 是否存在，不存在则跳转登录页并保存 redirect
  - afterEach：设置 document.title，dispatch addTab，persistTabs
- **输出/结果**：未登录用户被拦截，页面标题自动更新，标签自动创建
- **异常情况**：已登录用户访问登录页自动跳转首页
- **相关约束**：登录页不需要 token 校验

### 6.3.2 Deep-link 恢复

- **功能目的**：未登录用户访问深链接后，登录后自动恢复到目标页面
- **功能描述**：登录前保存目标 URL 到 localStorage（fmac_redirect），登录成功后读取并跳转
- **输入/触发条件**：未登录状态直接访问带参数的页面 URL
- **处理逻辑**：
  1. beforeEach 保存 redirect 到 localStorage
  2. 跳转 `/login?redirect=<目标URL>`
  3. 登录成功后读取 redirect（query 优先，其次 localStorage）
  4. `router.replace()` 恢复原地址
  5. afterEach 自动创建标签
- **输出/结果**：用户登录后自动跳转到原始目标页面
- **异常情况**：redirect URL 无效时跳转首页
- **相关约束**：登录成功后立即清除 localStorage 中的 redirect

## 6.4 标签页管理能力

### 6.4.1 标签页基础管理

- **功能目的**：提供企业级标签页浏览体验
- **功能描述**：路由切换时自动创建标签，支持点击切换、关闭、刷新等操作
- **输入/触发条件**：路由 afterEach 自动触发标签创建
- **处理逻辑**：
  - 标签已存在（path 相同）：不重复创建
  - `/login` 页面不创建标签
  - 首页标签不可关闭（closable: false）
  - 子应用页面（isSubApp: true）不参与 keep-alive 缓存
- **输出/结果**：标签栏展示当前打开的所有页面
- **异常情况**：路由数据缺失 title 时使用默认值
- **相关约束**：标签 id 由 path + 排序后 query 组合生成

### 6.4.2 标签页右键菜单

- **功能目的**：提供丰富的标签操作方式
- **功能描述**：右键标签弹出菜单，支持 6 种操作
- **操作列表**：
  1. 刷新：重新渲染当前页面
  2. 关闭当前：关闭当前标签
  3. 关闭其他：只保留当前标签和固定标签
  4. 关闭左侧：关闭当前标签左侧的所有标签
  5. 关闭右侧：关闭当前标签右侧的所有标签
  6. 关闭全部：关闭所有可关闭标签，跳转到首页

### 6.4.3 标签页拖拽排序

- **功能目的**：允许用户自定义标签顺序
- **功能描述**：使用 HTML5 Drag and Drop API 实现拖拽重排
- **输入/触发条件**：鼠标拖拽标签
- **处理逻辑**：dragstart 记录起始位置 → dragover 标记悬停位置 → drop 计算目标位置 → dispatch reorderTabs → persistTabs
- **输出/结果**：标签顺序更新，持久化到 localStorage
- **异常情况**：拖拽到容器外恢复原位
- **相关约束**：首页标签可被移动位置

### 6.4.4 标签页双击关闭

- **功能目的**：快速关闭不需要的标签
- **功能描述**：双击标签关闭该标签
- **输入/触发条件**：双击标签
- **处理逻辑**：检查 closable 属性，可关闭则执行关闭
- **输出/结果**：标签关闭，跳转到相邻标签
- **异常情况**：固定标签（首页）双击无反应

### 6.4.5 标签页持久化与恢复

- **功能目的**：浏览器刷新或重新登录后恢复工作状态
- **功能描述**：标签列表持久化到 localStorage，应用启动时自动恢复
- **输入/触发条件**：
  - 保存时机：afterEach、标签关闭/排序后
  - 恢复时机：应用启动时（token 存在时）
- **处理逻辑**：序列化 visitedViews 存入 `fmac_tabs` key，启动时反序列化恢复
- **输出/结果**：刷新后标签列表完整恢复
- **异常情况**：keep-alive 缓存不持久化，恢复后页面重新渲染（符合预期）
- **相关约束**：登出时清除持久化数据

## 6.5 页面缓存能力

### 6.5.1 keep-alive 缓存

- **功能目的**：页面切换时保留组件状态，避免重复渲染
- **功能描述**：使用 Vue2 keep-alive 组件，动态 include 绑定 cachedViews
- **输入/触发条件**：页面切换
- **处理逻辑**：
  - 主应用页面：keepAlive 默认 true，组件名加入 cachedViews
  - 子应用页面：isSubApp 为 true，不参与 Vue 缓存
  - 关闭标签时：从 cachedViews 移除，keep-alive 自动驱逐
  - 刷新页面时：移除缓存 → viewKey++ 重建 → 恢复缓存
- **输出/结果**：主应用页面状态保留，子应用页面由 qiankun 管理
- **异常情况**：组件未设置 name 属性时无法匹配缓存
- **相关约束**：子应用页面不使用 keep-alive

### 6.5.2 页面刷新机制

- **功能目的**：支持强制刷新当前页面
- **功能描述**：通过移除缓存 + 重建组件实现刷新
- **输入/触发条件**：右键菜单刷新 / 子应用 TAB_REFRESH 事件
- **处理逻辑**：
  1. dispatch refreshTab
  2. REMOVE_CACHED_VIEW（keep-alive 驱逐）
  3. Vue.nextTick → SET_ROUTER_VIEW_STATE（viewKey++）
  4. Vue.nextTick → ADD_CACHED_VIEW（恢复缓存）
- **输出/结果**：页面重新渲染，标签保持不变
- **异常情况**：其他缓存页面不受影响

## 6.6 主子应用通信能力

### 6.6.1 基座 → 子应用通信

- **功能目的**：基座向子应用同步全局状态
- **功能描述**：通过 qiankun initGlobalState 发送 token、userInfo、menu、permission
- **输入/触发条件**：登录成功后、状态变更时
- **处理逻辑**：`platform/bridge.js` 封装 syncUserState、syncMenuState 方法
- **输出/结果**：子应用通过 onGlobalStateChange 接收状态变更
- **异常情况**：子应用未挂载时状态变更不会丢失，mount 时通过 props 获取初始状态

### 6.6.2 子应用 → 基座通信

- **功能目的**：子应用向基座发送操作指令
- **功能描述**：子应用通过 setGlobalState 发送 route、refresh、logout、TAB_OPEN、TAB_CLOSE、TAB_REFRESH 等指令
- **输入/触发条件**：子应用需要跳转、刷新、退出或管理标签时
- **处理逻辑**：子应用 `context.js` 封装 navigateTo、requestRefresh、requestLogout 等方法
- **输出/结果**：基座 bridge.js 监听并处理对应指令
- **异常情况**：指令格式不正确时忽略处理
- **相关约束**：子应用之间不直接通信，所有跨应用交互通过基座中转

### 6.6.3 标签页事件同步

- **功能目的**：子应用可通知基座管理标签页
- **功能描述**：子应用通过 globalState 发送 TAB_OPEN/TAB_CLOSE/TAB_REFRESH 事件
- **输入/触发条件**：子应用需要打开/关闭/刷新标签页时
- **处理逻辑**：bridge.js 的 initBridge 监听全局状态变化，dispatch 对应 tabs action
- **输出/结果**：基座标签页状态同步更新
- **异常情况**：事件数据不完整时忽略处理

## 6.7 子应用适配能力

### 6.7.1 标准化适配流程

- **功能目的**：为子应用提供统一的接入规范
- **功能描述**：每个子应用仅需新增 3 个文件 + 改造 2 个文件即可接入基座
- **适配清单**：
  1. 新增 `public-path.js`（~5行）：动态设置资源路径
  2. 改造 `main.js`：导出 qiankun 生命周期（bootstrap/mount/unmount）
  3. 新增 `context.js`（~20行）：与基座通信模块
  4. 改造 `request.js`：适配 token 规范和 401/418 处理
  5. 改造 `webpack.config.js`：dev-server 添加 CORS 头
- **输出/结果**：子应用可被基座加载，同时保留独立运行能力
- **相关约束**：不动业务代码，保留工程结构

### 6.7.2 独立运行兼容

- **功能目的**：适配后子应用仍可在非 qiankun 环境下独立启动
- **功能描述**：通过 `window.__POWERED_BY_QIANKUN__` 判断运行环境
- **输入/触发条件**：子应用启动时
- **处理逻辑**：非 qiankun 环境直接 render()，qiankun 环境等待 mount 调用
- **输出/结果**：两种模式均可正常运行
- **相关约束**：路由 base 根据运行环境动态切换

## 6.8 构建与部署能力

### 6.8.1 独立构建

- **功能目的**：各应用独立构建，互不影响
- **功能描述**：每个应用拥有独立的 webpack 配置和构建脚本
- **输入/触发条件**：执行 `npm run build`
- **处理逻辑**：Webpack 4 编译 Vue SFC、JS、CSS，生成 dist 产物
- **输出/结果**：生成可部署的 dist 目录
- **异常情况**：编译错误时中断构建并报告
- **相关约束**：使用 CommonJS 配置体系

### 6.8.2 Nginx 部署

- **功能目的**：支持多种部署方案
- **功能描述**：提供多域名和单域名两种 Nginx 配置方案
- **多域名方案**：各子应用使用独立域名
- **单域名方案**：所有应用共用域名，通过路径区分
- **输出/结果**：Nginx 正确路由分发请求到各应用
- **相关约束**：子应用需返回 CORS 头

### 6.8.3 环境配置管理

- **功能目的**：区分不同环境的配置
- **功能描述**：每个应用包含 .env.dev / .env.test / .env.prod 三个配置文件
- **输入/触发条件**：构建时通过 `--env` 参数选择环境
- **处理逻辑**：构建时读取对应环境文件，注入 VUE_APP_BASE_API 等变量
- **输出/结果**：构建产物包含对应环境配置

# 8. 约束与限制

## 8.1 技术栈约束

- 必须兼容 Node.js 18 运行环境
- 必须兼容 Webpack 4 构建体系
- 必须兼容各子应用现有技术栈（假设均为 Vue 2.x）
- 适配后子应用必须保留独立运行能力

## 8.4 部署约束

- 各子应用独立部署
- 需支持多域名和单域名两种部署方案
- 子应用 dev-server 需返回 CORS 头

## 8.5 迁移约束

- 新老系统可并行运行
- 渐进式接入子应用，分三批改造
- 迁移过程中不能影响现有业务正常使用
