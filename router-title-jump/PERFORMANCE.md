# 性能报告（PERFORMANCE）

度量核心管线：**解析 → 别名/文件解析 → 建索引 → 搜索**。VSCode 的 `findFiles` 由宿主完成且很快，
真正成本在这条管线，因此基准脱离宿主直接度量（`scripts/bench.js`）。

```bash
npm run bench [路由数=1000] [模块文件数=20]
```

## 实测（Apple Silicon / Node 24；合成项目，每路由含 1 个 .vue + 中文 title）

| 指标 | 1000 路由 / 20 文件 | 3000 路由 / 40 文件 |
|---|---:|---:|
| 首次全量扫描 | **74.5 ms** | **151.1 ms** |
| 单路由均摊 | 74.5 µs | 50.4 µs |
| 增量：重扫单个模块文件 | **2.5 ms** | **3.2 ms** |
| 索引规模 | 1000 | 3000 |

搜索延迟（每查询 50 次取均值）：

| 查询 | 类型 | 1000 路由 | 3000 路由 |
|---|---|---:|---:|
| `产品` | 中文包含 | 0.57 ms | 1.22 ms |
| `cp` | 首字母 | 0.34 ms | 1.11 ms |
| `chanpin` | 全拼子串 | 0.36 ms | 1.03 ms |
| `/m1` | Router Path | 0.78 ms | 1.72 ms |
| `page5` | 文件名 | 0.42 ms | 1.06 ms |
| `yonghu` | 全拼 | 0.30 ms | 0.90 ms |

## 结论

- **QuickPick 打开**：首扫惰性触发，1000/3000 路由为 ~75/150ms 的一次性开销；此后命中 mtime 缓存，
  再次打开近乎零成本。远优于旧实现「每次保存即全量失效、下次打开全量重扫」。
- **搜索**：3000 路由级仍 **< 2ms**，大幅优于 100ms 目标。分档打分 + 每记录短路 + 预计算拼音，
  避免运行时重复转换。
- **增量更新**：单文件 2–3ms，改一个路由文件只重解析该文件。
- 移除旧 `findFiles` 200 条上限；别名/项目根解析整根一次并缓存（旧实现每路由重复读盘）。

## 达标对照（需求「十一、性能优化」）

| 目标 | 结果 |
|---|---|
| 1000+ 路由、10000+ vue | 首扫线性可扩展（~50–75µs/路由）；搜索与规模弱相关 |
| 首次扫描尽量快 | 惰性 + mtime 缓存 + 整根别名一次 |
| 之后全部增量 | watcher 按文件增量，未变文件复用 |
| QuickPick < 100ms | 搜索 < 2ms（打开成本主要在首扫，且可缓存） |
| 不遍历所有字段 | 预计算 + 分档短路 + 倒排候选 |

## 可继续优化的方向

1. **索引持久化**：将 `RouterIndex` 序列化到 `context.globalStorageUri`，冷启动直接反序列化，
   首扫降为「仅校验 mtime 变更的文件」。
2. **glob 展开**：`import.meta.glob` / `require.context` 结合文件系统展开为逐文件条目
   （需兼容宿主 Node 版本，避免依赖 `fs.globSync`）。
3. **前缀 Trie**：若单库路由达 5w+ 且搜索出现压力，可为 token 建 Trie 把前缀查询降到 O(len)；
   当前规模下扫描已足够快，暂不需要。
4. **并行解析**：首扫时用 worker 线程并行解析路由文件（大 monorepo 收益明显）。
5. **AST 缓存**：对同一文件缓存 AST，跨「别名提取」与「路由解析」复用。
