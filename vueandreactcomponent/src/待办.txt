三、报告业务状态模型

前端统一使用以下状态常量：

PARSING：草稿-解析中
PENDING：草稿-待确认
PUBLISHED：已发布
INVALID：已失效
FAILED：解析失败

注意：需求描述中既有四态，也有解析失败状态和草稿概念，存在口径不完全统一的问题。

本 Demo 使用五个前端业务状态保证功能闭环，FAILED 作为解析异常状态。

所有模拟接口使用统一状态枚举，不允许页面中散落不同状态字符串。

状态流转：

新建上传：
上传成功 → PARSING
解析成功 → PENDING
解析失败 → FAILED

保存草稿：
PENDING → PENDING

提交发布：
PENDING → PUBLISHED

下架：
PUBLISHED → INVALID

重新上架：
INVALID → PUBLISHED
前提是内容已经确认并完成必要校验。

重新解析：
PENDING / FAILED / INVALID → PARSING
解析成功 → PENDING

编辑已发布报告：
进入确认页面后可修改内容，但不得直接覆盖对客已发布内容。
需要在 Mock 中区分编辑中的内容与已发布快照。
重新解析和保存也不能让未确认内容直接对客生效。

删除：
PENDING / INVALID / FAILED 可以删除。
PUBLISHED 必须先下架。
PARSING 禁止删除。

如果状态规则出现需求冲突，以安全且可理解的交互实现，并在最终报告中注明。

本地 Mock 不必生成真实 PPTX/PDF 文件。
如果原文件来自浏览器真实上传，可以使用浏览器对象 URL 预览原始文件。
PDF 优先使用浏览器内置预览。
PPTX 不允许伪装成可直接浏览的 PDF。
对 PPTX 提供原文件下载或明确的“当前 Mock 不支持在线渲染”提示。

注意：
以上 I-02 到 I-10 的 URL 和 HTTP Method 属于 Demo 约定，除 I-01 外，原始接口说明并未提供完整路径及方法。
必须将这些约定集中放入 API 常量，方便以后与后端实际接口对接。

十二、Axios Mock 实现要求

1. 不依赖真实后端。
2. 使用 Axios 自定义 adapter 或等价 Axios 请求拦截方案。
3. Mock 只拦截本功能的 /api/mr/ 请求。
4. 不拦截现有项目其他 Axios 请求。
5. 组件中所有读取和写入都经过 Axios。
6. Mock 返回统一响应结构：
   code
   message
   data
7. 请求延迟模拟约300至800毫秒。
8. 解析任务采用异步状态变化。
9. 数据持久化使用 localStorage，刷新后保留报告数据。
10. File、Blob 及 ObjectURL 不直接 JSON 序列化到 localStorage。
11. 通过内存文件缓存和元数据区分真实文件和持久化数据。
12. 页面刷新后若原始二进制文件已不可用，必须明确提示需要重新选择文件，不能提供损坏的文件流。
13. 提供恢复初始 Mock 数据的开发方式。
14. 初始模拟数据覆盖 PENDING、PUBLISHED、INVALID、FAILED 等状态。
15. 使用确定性的 Mock 数据，避免每次刷新随机变化。

十三、乐观锁与业务一致性

Mock 每条记录包含 version。

保存、发布、下架、重新解析、删除时：
必须校验请求 version 与当前记录 version 一致。

不一致返回业务错误：
数据已被其他操作修改，请刷新后重试。

成功写操作后：
version + 1。

前端写操作成功后：
刷新详情或列表，更新最新版本。

禁止使用旧 version 连续提交写操作。

同月份新增报告：
需要重新检查唯一性。
不允许通过绕过月份选择器重复创建有效报告。

发布：
必须重新校验状态和内容完整性。

删除：
必须校验允许删除的状态。

解析中：
不得重复提交解析任务。

异步解析完成：
需要更新状态、时间和版本。

同月份仅允许一个有效报告对客展示。

进入 PARSING 状态。
异步生成五类资产观点。
约2至4秒后完成。
成功进入 PENDING。
