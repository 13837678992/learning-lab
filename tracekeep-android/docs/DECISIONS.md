## D-001 不集成第三方工具（已确认）

**决策**：本 App 的 APK 不包含 AndroidQF、MVT、ALEAPP、DroidCustos 的任何代码、二进制或运行时组件。

**理由**：
1. 四个项目均为桌面电脑 + ADB 工具，无法在 Android 手机上运行，对端上录制/采集无复用价值（详见 `OPEN_SOURCE_ASSESSMENT.md` §1、§5）。
2. MVT License 1.1 含第 3.0 条「同意使用限制」（数据所有者须明确、知情、无胁迫同意），作为分发物的一部分会给 App 分发引入额外合规复杂度；MVT 官方自认该许可证不符合 OSI 开源定义。
3. DroidCustos 为 GPL-3.0-or-later，代码级复用将触发传染义务。
4. `PROJECT_REQUIREMENTS.md` §2 要求「无广告、分析或默认上传 SDK」，引入无关第三方组件与其精神相悖。

**允许的交互方式**（不构成集成）：文档推荐用户自行安装的桌面伴侣工具；证据包可选导出「兼容格式」供桌面工具消费；借鉴设计模式后干净重写。

## D-002 AndroidQF 归档结构仅作可选兼容参考（已确认）

**决策**：可将 AndroidQF 公开归档结构（ZIP + `acquisition.json` 风格元数据 + `hashes.csv` 风格清单）作为**可选导出变体**的格式参考，但：
- 只对齐公开文件结构（格式层面），不复制其代码；
- 在完成实际桌面消费实测之前，任何文档、界面与报告**不得**宣称「兼容 MVT/ALEAPP/AndroidQF」或「已被某某工具支持」；
- 兼容格式导出不得影响原始证据包的生成与校验（导出失败不得影响主包）。

**已核实的相关事实**（2026-10-29，源码核对）：MVT 与 DroidCustos 均**不校验** androidqf 的 `hashes.csv`；androidqf 自身无归档验证子命令。跨工具流转的完整性责任在使用方，TraceKeep 若做兼容导出必须自带校验工具与说明。

## D-003 法律与服务调研为独立任务（已确认，任务未完成）

**决策**：可信时间戳、电子认证、第三方电子数据存证、公证四类服务的调研，作为独立任务执行，交付 `docs/LEGAL_AND_SERVICE_ASSESSMENT.md` 与 `docs/LEGAL_QUESTIONS_FOR_COUNSEL.md`（见 `TECHNICAL_PLAN.md` §7）。硬性约束：
- 未核实服务主体、条款、接口和价格之前，不得硬编码供应商、虚构接口或声称已接入（需求 §1、§10 阶段 8）；
- 应用界面与报告必须如实显示「本次记录没有第三方时间戳/存证」的状态；
- 不得把付费服务设为应用运行前提。

**当前状态**：未完成。在完成并确认前，阶段 8（第三方适配器）不得开工；首版仅实现 `TimestampProvider` / `EvidencePreservationProvider` / `SignatureProvider` 接口层与「未存证」状态显示。

### D-012 模块结构定型（已确认，阶段 1 实测）
**决策**：10 模块结构如下（`settings.gradle.kts` 固定）：
- 纯 Kotlin JVM 模块：`core:model`（数据模型，不依赖 Android）、`core:integrity`（哈希/链，可在 JVM 单测与桌面验证复用）、`core:verify`（独立验证核心，**支撑需求 §6「独立验证不依赖原 App 数据库」**）；
- Android library 模块（空骨架，阶段 2+ 填充）：`core:storage`、`core:crypto`、`core:location`、`core:timestamp`、`core:provider`、`core:export`；
- `app`（Compose 骨架界面）。
**理由**：把可离线验证的核心逻辑放在 JVM 模块，确保阶段 10 的独立验证工具不需要 Android 运行时。

### D-013 隐私与文案基线（已确认，阶段 1 实测）
**决策**：
- `android:allowBackup="false"`（证据材料不进系统备份通道；`THREAT_MODEL.md` P-5 缓解）；
- 阶段 1 不声明任何系统权限（合并清单核验：无 `uses-permission`，仅 androidx 注入的签名级自权限）；**阶段 3 起按功能需求逐项增补权限并在执行日志中列明**；
- 文案纪律常量 `LegalCopy`（需求 §12 推荐表述 + 禁止清单）落地为 `core:model` 代码 + 强制单元测试；后续界面/报告文案必须引用该常量。

### D-014 `core:storage` 为纯 JVM 模块（已确认，阶段 2 实测）
**决策**：存储核心（EvidenceStore/AtomicFiles/PathSafety）不依赖 Android API，作为纯 Kotlin JVM 模块实现；Android 端只负责把应用私有目录（`filesDir`）传入。
**理由**：单元测试无需模拟器/真机；字节级格式实现可被独立验证工具（阶段 10）直接复用，支撑「独立验证不依赖原 App 数据库」的硬性要求。

### D-015 暂不引入 Room（已确认，阶段 2 实测）
**决策**：证据账本采用版本化 JSON（session.json/files.json/seal.json）+ 追加式 JSONL（events.log/locations.jsonl）。**暂不引入 Room**。
**理由**：需求 §2 允许 Room 但未强制；当前查询/保全需求被文件账本完整覆盖；减少依赖与「数据库与文件不一致」风险面（THREAT_MODEL X-3）。如 UI 层出现明确性能需求，再评估引入并更新本决策。

### D-016 `core:recording` 编排模块（已确认，阶段 3）
**决策**：录音编排逻辑（会话状态机接线、文件登记/封装、异常处置）放在新增的纯 JVM 模块 `core:recording`，通过 `AudioRecorderEngine` 接口抽象实际录音引擎；Android 实现（MediaRecorder + 前台服务）在 app 层注入。**理由**：控制逻辑可 JVM 单测（含故障注入），与 Android 框架解耦。
